1. WHAT WE ARE BUILDING

A high-velocity B2B event networking prototype for a founder preparing an a16z
Speedrun application. The founder supplied an application window of October 12
to November 1, 2026; this window has NOT been independently verified. Verify it
from official sources if using it for application scheduling or external copy.

Core question:
"Given who I am, what I want, and this event's attendee list, which 5–10 people
should I make a point of meeting, why, and how should I start the conversation?"

The longer-term room size is approximately 3,000 attendees. The immediate
validation dataset should contain only 20–30 real attendees. Earn confidence in
identity resolution and shortlist quality before expanding volume or UI scope.

The product turns raw names, companies and job titles into an evidence-backed,
personalized shortlist. Strategic value can come from:
- A match to the user's target customer or partner profile.
- A relevant founder or investor.
- A connector with an evidenced relevant portfolio/community/network role.
- A professional background overlap that creates a useful conversation opening.

"Predictive heat map" and "identity-routing engine" are product aspirations.
The current implementation is a ranked JSON pipeline, not a physical venue map,
trained predictive model, real-time location system or calibrated probability.

Founder hypothesis: static guest sheets and existing event-networking workflows
leave too much work to the attendee. Whova and Brella were named as comparison
products in the original brief. Do not assume their current capabilities are
limited to a phonebook without research. The brief's "90% of time wasted" is
positioning language, not a measured statistic.

4. ORIGINAL MVP REQUIREMENTS

A. Ingest CSV or JSON with these exact required headers/keys:
   Attendee Name | Current Company | Job Title
B. Use a live enrichment provider to resolve Name + Company to a LinkedIn profile.
C. Enrich profile summary/about, current role, past jobs and recent public posts.
D. Evaluate each attendee against a configurable enterprise ICP with structured

Implemented pipeline:
1. Validate CSV/JSON, preserve invalid rows, collapse identical name/company/title

3. A conservative identity gate decides whether scoring is allowed.
4. Optional HarvestAPI LinkedIn profile posts actor on Apify fetches recent posts.
5. GPT-4o Structured Outputs evaluates five dimensions, reason, hook and gaps.
6. Python computes a deterministic weighted relevance score and sorts results.
7. JSON holds the ranked list, top candidate IDs and a separate review/error queue.

6. IDENTITY AND EVIDENCE CONTRACT — PRESERVE THIS

Name + company cannot guarantee an exact, independently verified identity.
Accepted matches are high_confidence_match with verified:false, not "verified
by LinkedIn". Do not turn a provider score of 8/10 into "80% confidence".

Current gate requires:
- PDL likelihood >=8 by default (--min-likelihood accepts 6–10).
- Both name and company reported as matching by PDL.
- A provider-returned LinkedIn personal-profile URL passing structural checks.
- Current company matches after conservative case/whitespace/legal-suffix cleanup.

PDL's company input can match past employment. A former employer, unexplained
alias or uncertain match therefore goes to needs_review. No LLM scoring should
proceed on an unresolved or ambiguous identity. Failure is score:null, not 1/10.

PDL summary is the about-equivalent, not a separately retrieved About field.
Nulls remain explicit. Only a bounded set of professional fields is used as LLM
evidence; personal contact and home address data are not included in that payload.

The posts adapter requests up to five original posts, filters author identity,
and requires a timestamp within the last 90 days. Missing/failed posts are
explicit. Never invent a post, shared connection or mutual work history.
A shared employer does not imply two people knew each other or worked together.

Evidence IDs and source URLs accompany the score and text. The code checks that
IDs exist; it does NOT mechanically prove that every generated claim is entailed
by that evidence. Structured Outputs guarantees shape, not factual correctness.

7. SCORING CONTRACT

Default weights:
role_fit          30% — relevant founder/investor role
topic_fit         30% — AI developer tools relevance
active_intent     20% — explicit evaluation/buying/partner/investment signal
connector_value   10% — evidenced relevant network access/activity
shared_background 10% — supported overlap with requester context

Each dimension receives 0–10 plus evidence IDs. Unknown/missing evidence scores
zero for that dimension and should appear as a data gap. The displayed score is:
max(1, sum(dimension_rating * weight) / sum(weights)), rounded to two decimals.

The model must not infer buying intent from title, prestige or AI keywords.
Connector value needs actual evidence; follower count alone is insufficient.
These are heuristic relevance scores, NOT likelihood of conversion or willingness
to meet. Sparse profiles may rank lower even when the real person is relevant;
measure that bias during evaluation instead of hiding missingness.

icp.json contains target text, dimension criteria, weights, requester context,
exclusions and minimum_shortlist_score (default 6). The top list contains up to
--top-k (default 10) distinct resolved identities meeting that threshold. Fewer
than five is acceptable when evidence is insufficient. Never pad the shortlist.

The founder's background and the target ICP are different inputs. Preserve that
distinction; do not silently turn every run into a personal job-search matcher.

8. EXISTING RELIABILITY MEASURES AND LIMITS

- SQLite caches enrichment/scoring; keys include relevant configuration/evidence.
- 24-hour default cache TTL; recent posts have a separate 24-hour cache.
- TTL stops reuse but does not physically purge expired records from storage.
- Atomic output writes and per-attendee checkpoints.
- Bounded retries with backoff/jitter, Retry-After handling and timeouts.
- Core auth/quota errors halt with partial output; optional post failures degrade.
- A persistent guard prevents blindly replaying an uncertain paid Apify POST.
- Logs avoid raw keys, names, provider responses and attendee data.
- Refusals, truncated model output and invalid evidence references become errors.
- The loop is SEQUENTIAL with request pacing, not parallel/batch high throughput.
- Token throttling is reactive 429 handling, not a shared token-budget scheduler.
- Rewriting the whole matrix after every row may become costly for large lists.
- Run only one process per cache/output file under the present design.
- Credentials are read from environment variables; .env is not loaded automatically.

The present tests cover ingestion/deduplication, identity gating, URL spoof
rejection, stale/wrong-author posts, evidence validation, model refusals and
truncation, retries/quota, uncertain paid-call replay prevention, cache expiry,
mocked live-flow recovery, partial output, ranking, exclusions and a no-network demo.
They do not establish provider availability, matching accuracy or human utility.

9. HOW TO RUN

From the extracted event-router directory:

    python3 --version
    python3 -m unittest -v
    python3 event_router.py sample_attendees.csv --demo --output demo_output.json

Demo mode never calls providers. Its scores are fixed fictional fixtures, not
inference results, and its sample identities are not real networking leads.

Live mode requires environment variables supplied securely by the founder:
    PDL_API_KEY
    OPENAI_API_KEY
    APIFY_TOKEN     (only when --posts is enabled)

Do not ask the founder to paste secrets into chat or commit them. Explain how
to set them locally using her environment's secure workflow. Never print them.

    python3 event_router.py attendees.csv --icp icp.json --limit 20 \
      --top-k 10 --output prioritized.json

Add --posts only when the Apify credential and budget are available.

Exit codes:
0 = completed; unresolved/review rows can still exist.
1 = completed with issues, including an intentional --limit or optional-post failure.
2 = configuration/fatal error or interruption.

Do not mistake exit 1 after a limited pilot for a total failure. Inspect the
JSON's run_status, fatal_error, timestamps and per-row status. A startup config
error can leave an older output untouched.
